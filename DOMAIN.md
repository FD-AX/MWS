# Предметка кейса NET: что такое «потоки» и «витрины» и кто их пишет

Конспект от 2026-09-02 (разбор формулировки «аналитики готовят ТЗ на разработку новых потоков и витрин данных»).

## Контекст продукта

«Поставка данных из источников радиосети» = команда дата-платформы телеком-оператора. Радиосеть = RAN (radio access network): базовые станции и всё вокруг них. Источники — OSS-системы вендоров (класс Huawei U2020 / Ericsson ENM / Nokia NetAct), из которых идут:

- **PM (performance measurements)** — счётчики производительности: тысячи метрик с каждой БС (трафик, drop rate, доступность, качество сигнала);
- **CM (configuration management)** — конфигурация: параметры сот, частоты, соседства;
- **FM (fault management)** — аварии/алармы оборудования;
- геоданные, справочники сайтов.

Команда NET забирает это и «поставляет данные» потребителям: планирование/оптимизация сети, качество, отчётность, ML-команды.

## Термины

**Поток данных** = ETL/ELT-пайплайн: регулярный процесс «забрать из источника → распарсить → почистить → загрузить в хранилище». ТЗ на поток: источник (интерфейс/файлы/API, формат), расписание, целевые таблицы детального слоя, маппинг полей, правила обработки.

**Витрина данных** = data mart: производная таблица (или набор) под конкретную аналитическую задачу, собранная из детального слоя. ТЗ на витрину: структура целевой таблицы + source-to-target mapping + формулы показателей + гранулярность/ключи + периодичность пересчёта.

**Аналитик** здесь = аналитик данных / системный аналитик DWH-команды (не бизнес-аналитик приложений): знает предметку и переводит её в спецификацию для разработчиков (SQL/Spark/Airflow). ТЗ живут в Confluence по шаблону (кейс явно исключает интеграцию с Confluence из скоупа — значит, вход просто текст).

## Откуда боль (типовые дыры в таких ТЗ)

- «Загружаем ежедневно и добавляем в витрину» → инкремент по какому полю? окно перезагрузки?
- Late-arriving data: для RAN-счётчиков норма — БС может отдать файлы за вчера. Что с ними?
- Дедупликация при повторной выгрузке: по какому ключу, какая запись выживает?
- Счётчик не пришёл → NULL или 0? Для KPI-формул это разные результаты.
- Деление на ноль в формуле (drop rate при нуле попыток) — что возвращать?
- Поле в маппинге без источника; формула ссылается на неописанный счётчик.
- «Сота»/«ячейка»/«cell» — одна сущность под тремя именами.
- Нет времени готовности данных (SLA) — только «ежедневно».

Каждая дыра = возврат ТЗ аналитику + пересогласование + правки в разработке/тестировании. Это и есть стоимость проблемы из кейса.

## Следствия для ревьюера

Главные объекты проверки: таблица маппинга (полнота, согласованность с источником), формулы показателей (все входы определены, края обработаны), инкрементальная логика, правила NULL/дублей, расписание и SLA. В обезличенных примерах имена заменят на нейтральные, но структура «источник → маппинг → трансформации → целевая таблица → регламент» останется — доменный чеклист из [RESEARCH.md](RESEARCH.md) ложится без переделок.
